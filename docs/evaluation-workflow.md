# 평가 운영 흐름

최초 평가는 로컬에서 시작합니다. 실제 답변과 검토 결과로 평가 절차를 확인한 뒤, 같은 명령을 CI에 연결합니다. 결과 공유는 PR 댓글과 디스코드 채널 알림으로 나눕니다. 디스코드 전송과 실제 WIKI 변경 PR 평가는 아직 구현하지 않았습니다.

## 무엇이 평가를 시작하나

| 방식 | 시작 계기 | 사용하는 상황 | 목표 결과 채널 |
| --- | --- | --- | --- |
| 수동 평가 | 사람이 로컬 명령 또는 GitHub의 수동 실행 버튼을 누름 | 최초 평가, 모델·자료 변경 실험, 특정 사례 재확인 | 결과 파일 + 디스코드 웹훅 알림 |
| WIKI PR 평가 | WIKI·Skill 변경 PR을 생성하거나 갱신함 | 수정 전후 비교와 기존 사례의 회귀 확인 | 결과 파일 + 해당 PR의 평가 댓글 갱신 |

수동 평가는 실행 장소를 뜻하지 않습니다. 로컬에서도 CI에서도 사람이 시작할 수 있고, 두 곳 모두 실제 Claude 응답을 받으려면 모델을 호출해야 합니다. 기본 데모는 고정 응답으로 도구의 동작만 확인합니다.

현재 자동 실행되는 것은 **이 평가 도구 레포의 공개 예제 검사**입니다. WIKI 레포의 변경을 감지하거나 실제 WIKI의 모델 응답을 자동 평가하지는 않습니다. 현재 모델용 workflow도 비공개 레포의 수동 실행만 허용하므로, PR 이벤트를 추가하는 작업과 실행 범위 검증이 필요합니다.

## 적용 순서

1. **로컬 최초 평가:** 사람이 원문과 정답을 확인한 소수 사례로 A/B/C를 실행합니다. 실제 모델 연결, 입력 자료, 판정 기준과 검토 양식이 맞는지 확인합니다. [첫 실제 평가 준비](first-evaluation.md)의 순서를 사용합니다.
2. **결과 전달:** 기존 보고서를 기준으로 읽기 쉬운 결과 요약과 디스코드 알림을 추가합니다. 실패 원인과 다음 작업이 보이도록 하고, 사람 검토 후 재채점한 결과도 전달합니다.
3. **WIKI CI 연결:** 수동 CI 실행부터 확인하고 WIKI·Skill 변경 PR에 연결합니다. 변경된 문서와 평가 사례의 대응 관계를 정해 평가 범위를 선택합니다. 범위를 확정할 수 없으면 전체 사례를 실행하거나 선택이 불가능한 이유를 표시하고, 조용히 생략하지 않습니다.

현재 Claude 연결 코드는 로컬에서도 API 키를 사용합니다. 구독 로그인으로 실행하는 방식은 구현되어 있지 않습니다. 인증이나 실행 방식을 바꾸면 기존 결과와 동일한 조건인지 먼저 확인합니다.

## 같은 결과를 두 채널에 전달하기

아래는 구현할 결과 전달 흐름입니다. 채널별로 따로 채점하지 않고, 같은 실행의 보고서에서 요약을 만듭니다.

```text
로컬 또는 CI에서 평가 실행
          ↓
모델 답변 저장 · 자동 검사 · 사람 검토
          ↓
report로 결과 생성
          ├─ PR 평가 → 같은 PR의 평가 댓글 갱신
          └─ 수동 평가 → 지정한 디스코드 채널에 알림
```

응답 수집과 자동 검사만 끝났다면 사람 검토 대기 상태를 먼저 전달합니다. 검토가 끝나면 저장한 응답에 `report --reviews ...`로 판정을 반영하고 결과를 갱신합니다. 답변이 그대로라면 알림이나 재채점을 위해 모델을 다시 호출할 필요는 없습니다.

요약에는 다음을 표시합니다.

- 평가 대상 커밋, 모델, 조건, 사례 수와 반복 횟수, 실행 식별자
- 실행 완료·오류·누락과 품질 판정(`PASS` / `FAIL` / `INCONCLUSIVE`)
- 자동 검사 실패와 사람 검토 대기 수, 검토한 항목의 심각도별 실패 수
- 실패한 이유, 근거와 개선 방향, 다음에 사람이 확인할 작업
- 접근 가능한 상세 보고서와 실행 기록 링크

실행 상태와 품질 판정은 구분합니다. 검토 전 결과를 통과로 표시하지 않으며, 이미 확인된 실패와 남은 검토가 함께 있으면 둘 다 남깁니다. 검토를 마쳤더라도 dev 파일럿만 있는 경우에는 holdout 판정이 `INCONCLUSIVE`로 남을 수 있습니다.

실패 이유는 자동 검사 결과와 사람의 항목별 판정에서 가져옵니다. 개선 방향은 채점 기준과 검토 의견에 근거해 작성하고, 근거가 없으면 추가 확인이 필요하다고 표시합니다. 평가 대상 모델의 자신감이나 자체 판정을 최종 결과로 사용하지 않습니다. 현재 보고서는 판정 이유를 제공하지만 별도의 개선 방향 작성 기능과 아래 전달 형식은 추가 작업입니다.

| 채널 | 표시 방식 |
| --- | --- |
| PR 댓글 | 요약을 먼저 보여주고, 실패 이유·개선 방향·상세 결과는 펼쳐서 확인. 재실행 시 같은 댓글 갱신 |
| 디스코드 웹훅 | 지정한 채널에 상태·핵심 결과·다음 작업과 보고서 링크 전달 |

디스코드는 DM이 아닌 채널 알림으로 사용합니다. 알림 전송만을 위해 별도 봇 서버를 만들지는 않습니다. 웹훅 URL은 로컬 환경 변수 또는 GitHub Actions secret으로 설정합니다. 공개 PR 댓글과 팀 채널은 열람 범위가 다르므로, 각 채널에 공개 가능한 내용만 요약에 넣습니다. 디스코드 안에서 검토를 승인하는 기능은 이 계획에 포함하지 않습니다.

전송이 실패해도 이미 저장된 평가 결과는 유지합니다. 알림만 다시 보내는 경우 같은 실행을 참조하고 모델 평가를 새로 시작하지 않도록 구현합니다. 로컬 파일 경로는 팀원이 열 수 있는 링크가 아니므로, 상세 결과가 공유 위치에 없으면 파일이 아직 로컬에 있다는 사실만 안내합니다.

## 기록 보관과 공개

Git에서 제외하는 것과 기록을 남기지 않는 것은 다릅니다. `local/`, `artifacts/` 등은 실행 자료를 일괄 커밋하지 않기 위한 기본값이며, 평가셋·보고서 전체를 비공개로 고정하는 정책은 아닙니다.

| 자료 | 보관 방식 |
| --- | --- |
| 실제 CS 원문, 학생 정보, 비공개 WIKI 자료 | 로컬 또는 접근을 제한한 팀 저장소 |
| 공개 가능한 질문·정답·채점 기준 | 내용과 출처의 공개 범위를 확인한 뒤 별도 경로에서 Git으로 버전 관리 |
| 모델 답변·검토 의견·결과 보고서 | 원본 실행을 보존하고, 공개 가능한 부분을 확인해 레포 문서나 PR에 공유 |
| 매 실행의 전체 로그·중간 파일 | 실행별 출력 폴더 또는 CI artifact |

공개용 사례는 `datasets/public/`, 공개 보고서는 `docs/evaluations/`처럼 실행 출력과 다른 경로에 둘 수 있습니다. 현재 공개 예제는 `sample/`에 있으며, 실제 공개 평가셋과 결과 보고서는 아직 등록하지 않았습니다. 생성한 파일이 자동으로 공개 경로로 복사되거나 커밋되지는 않습니다.

정답이 있다는 이유만으로 공개를 막지는 않습니다. 다만 공개 여부와 관계없이 평가받는 모델에는 정답·채점 기록을 입력하지 않으며, 실행 중 접근 범위도 분리해야 합니다. 공개해서 개선에 참고한 사례는 dev로 관리하고 독립 holdout 성과로 보고하지 않습니다.

공개 보고서에는 실행 날짜·식별자, 평가 엔진·자료·모델 버전, 사례 범위, 성공·실패·미검토 건수, 실패 이유, 수정 PR, 재평가 결과와 한계를 남깁니다. 내용을 가리거나 사례를 재구성했다면 그 범위를 표시합니다. 잘된 실행만 남기거나 실패를 새 결과로 덮어쓰지 않습니다.

로컬 파일을 Git에서 제외한 것만으로 팀 보관이 해결되지는 않습니다. 팀이 다시 검토할 원본은 접근 가능한 비공개 저장 위치에 보관합니다. 현재 비공개 CI artifact의 보관 기간은 7일이므로, 장기 비교에 사용할 기록은 만료 전에 따로 보관해야 합니다. PR 댓글과 디스코드 알림만을 원본 기록으로 사용하지 않습니다.

## 참고한 방식

[토스의 Skill 평가 글](https://toss.tech/article/skill-quality-rubric)은 PR 결과를 댓글로, 수동 실행 결과를 Slack DM으로 전달하고 문제의 이유와 수정 방향을 함께 보여줍니다. 여기서는 그 전달 방식을 참고하되 수동 평가 알림은 디스코드 웹훅으로 구성합니다. 해당 글은 원본 평가 파일의 Git 제외 여부를 설명하지 않으므로, 이 레포의 보관 정책을 토스의 내부 정책으로 설명하지 않습니다.

디스코드 메시지 전송은 [공식 웹훅 문서](https://docs.discord.com/developers/resources/webhook)를 기준으로 구현합니다. 현재 사용할 수 있는 명령과 CI 제약은 [GitHub Actions 연결](actions.md)에 정리했습니다.
