# 정답지 검토

평가 전에 질문·정답 초안·편람 근거가 맞는지 확인하는 작업입니다. AI가 작성한 초안이나 이미 해결한 CS를 가져왔더라도, 적용 학번과 예외 조건은 사람이 원문에서 확인해야 합니다.

검토 파일에는 처음 가져온 사례와 수정 중인 초안을 함께 보관합니다. 완료하지 못한 문항은 수정 필요나 보류로 남기고, 확인한 문항만 평가용 정답지로 내보냅니다. 모델 답변을 실행한 뒤 채점하는 `review-template`과는 별도 단계입니다.

## 검토 화면 열기

```bash
npm run build
node dist/cli.js oracle-review --cases local/cases.draft.jsonl \
  --out local/oracle-review.html --title "졸업요건 정답지 검토"
```

생성된 HTML 파일을 브라우저에서 엽니다. 별도 서버나 로그인, API 키는 필요하지 않습니다. 화면에 필요한 코드가 HTML 안에 들어 있으며 외부 CDN을 사용하지 않습니다. 명령은 원본 사례를 바꾸지 않고, 같은 출력 파일을 덮어쓰지 않습니다.

왼쪽 문항 목록에서 검토할 항목을 고르고, 질문·정답과 편람 근거를 함께 확인합니다. 검색과 상태 필터로 미검토·수정 필요·보류 문항을 모아볼 수 있습니다. 긴 근거와 채점 기준은 필요한 부분을 펼쳐 읽습니다.

새 검토는 모든 문항이 미검토로 시작합니다. 원본에 이전 검토 정보가 있더라도 새 확인을 요구합니다. 모델을 호출하거나 정답을 자동으로 승인하지 않습니다.

### 편람 페이지 연결하기

출처 발췌문은 사례 파일에서 표시합니다. PDF 원문까지 바로 열려면 출처 ID와 파일 위치를 연결한 JSON 파일을 준비합니다. 예를 들어 `local/source-links.json`을 다음처럼 작성합니다.

```json
{
  "handbook-2026-2": "source/handbook-2026-2.pdf#page=36"
}
```

키는 사례의 `sources[].id`와 같아야 합니다. 위 경로는 `local/source/handbook-2026-2.pdf`를 가리킵니다. 상대 경로는 명령을 실행한 폴더가 아니라 연결 JSON 파일이 있는 폴더를 기준으로 해석합니다. 페이지 번호는 PDF 뷰어의 페이지 번호입니다.

한 출처 ID에는 링크 하나를 연결합니다. 여러 문항에서 같은 ID를 사용하면 같은 페이지가 열리므로, 서로 다른 페이지를 가리켜야 한다면 원본 사례를 준비할 때 출처 ID도 구분합니다.

```bash
node dist/cli.js oracle-review --cases local/cases.draft.jsonl \
  --source-links local/source-links.json --out local/oracle-review-with-sources.html
```

로컬 PDF 경로와 HTTP(S) 주소를 사용할 수 있습니다. PDF를 HTML에 복사하거나 서버로 업로드하지 않으며, 원문 링크를 눌렀을 때 해당 파일을 엽니다. HTML을 다른 컴퓨터로 옮겼다면 그 컴퓨터의 PDF 위치로 링크를 다시 만들어야 합니다.

화면에서 근거의 위치·버전·발췌문을 수정하면 이전 원문 링크는 숨깁니다. 검토 파일을 저장하고, 수정한 출처에 맞춘 `--source-links`와 저장한 `--workspace`를 함께 지정해 새 HTML을 만들면 다시 연결됩니다.

## 저장하고 이어서 검토하기

**검토 파일 저장**을 누르면 문항별 수정 내용·상태·검토자·의견과 검토 위치가 담긴 JSON 파일의 다운로드를 요청합니다. 브라우저의 다운로드 폴더에서 파일을 확인하고 `local/` 등 본인이 관리하는 위치에 보관합니다. 아래 예시에서는 다운로드한 파일을 `local/oracle-review.json`으로 옮겼다고 가정합니다. 화면을 조작하는 것만으로 기존 사례 파일이나 HTML 파일이 수정되지는 않습니다.

다음에 같은 HTML을 열고 **검토 파일 불러오기**로 저장한 JSON을 선택합니다. 검토를 시작했던 원본 사례와 일치하는지 확인한 뒤 내용을 복원합니다. 다른 평가셋의 파일이나, 승인한 내용을 변경한 파일은 그대로 불러올 수 없습니다.

새 HTML을 만들면서 이전 검토를 넣을 수도 있습니다.

```bash
node dist/cli.js oracle-review --cases local/cases.draft.jsonl \
  --workspace local/oracle-review.json --out local/oracle-review-resumed.html
```

`--cases`에는 처음 검토를 시작했던 원본을 지정합니다. PDF 링크를 사용했다면 `--source-links`도 함께 지정합니다.

브라우저 임시 저장은 복구를 돕는 보조 수단입니다. 브라우저 설정, 비공개 모드, 저장 공간 제한이나 데이터 삭제에 따라 사용할 수 없으므로, 작업을 마칠 때는 **검토 파일 저장**으로 파일을 남깁니다. 복구할 기록이 발견되면 **이전 검토 이어서 보기** 또는 **현재 파일로 시작**을 선택합니다. 같은 평가셋을 다른 창에서도 수정한 경우에는 임시 저장 충돌 안내가 나타나며, 필요한 검토를 파일로 먼저 보관합니다.

### 화면 없이 검토 파일만 만들기

라이브러리나 별도 도구에서 검토 파일을 다루려면 `oracle-init`으로 빈 검토 상태를 생성할 수 있습니다. HTML을 사용하는 경우 이 명령을 먼저 실행할 필요는 없습니다.

```bash
node dist/cli.js oracle-init --cases local/cases.draft.jsonl \
  --out local/oracle-review.json --title "졸업요건 정답지 검토"
```

출력 파일이 이미 있으면 덮어쓰지 않습니다.

## 문항마다 확인할 것

1. 질문과 입력 조건만으로 답할 수 있는지 확인합니다. 정보가 부족하면 추가 질문, 규정이 충돌하면 사람 확인 요청을 정답으로 둘 수 있습니다.
2. 편람의 버전·페이지·적용 학번과 예외를 확인하고 정답 값을 수정합니다.
3. 출처의 발췌문이 결론을 뒷받침하는지, 채점 기준이 답변과 근거를 구체적으로 판단할 수 있는지 확인합니다.
4. 검토자와 필요한 의견을 남긴 뒤 문항 상태를 정합니다.

수정하려면 **질문·정답 수정**을 펼치고 **수정 내용 적용**을 누릅니다. 문항 이동이나 파일 저장 때도 유효한 입력은 자동 적용됩니다. JSON이나 필수 항목에 오류가 있으면 이동·저장을 멈추고 입력을 보존하므로, 내용을 고치거나 **입력 되돌리기**로 마지막 적용 상태로 돌아갑니다. 잘못된 JSON을 작성하던 중간 입력은 검토 JSON 파일로 내보낼 수 없습니다.

| 상태 | 의미 |
| --- | --- |
| `pending` | 아직 확인하지 않았거나, 확인한 내용을 수정해 다시 검토해야 함 |
| `needs_changes` | 고칠 부분을 찾았으며 수정이 남아 있음 |
| `on_hold` | 추가 자료나 담당자 확인이 필요해 판단을 보류함 |
| `approved` | 검토자가 정답·근거·채점 기준을 확인함 |

확인 완료에는 검토자 이름이 필요합니다. 확인 시점은 완료할 때 기록합니다. 완료한 뒤 초안, 검토자 또는 의견을 바꾸면 이전 완료 상태가 해제되며 다시 확인해야 합니다.

검토 중에는 질문, 입력 조건, 정답, 근거, 채점 기준, 태그를 수정할 수 있습니다. 사례 ID, 규정군, dev/holdout 구분, 실제·가상 구분과 독립 원출처 여부는 고정합니다. 이 항목을 고쳐야 한다면 원본 사례를 수정한 뒤 새 검토를 시작합니다.

## 저장한 검토와 원본 연결

검토 파일에는 원본 사례·평가셋의 내용 해시와 승인한 내용의 해시를 기록합니다. 다른 평가셋의 검토 파일을 잘못 가져오거나, 승인한 정답을 바꾼 채 완료 상태를 유지하는 일을 막기 위한 장치입니다. 해시를 직접 고쳐 이전 검토를 재사용하지 않습니다.

라이브러리에서는 `createOracleWorkspace`, `validateOracleWorkspace`, `updateOracleEntry`, `exportOracleCases`를 사용합니다. 저장된 파일을 읽을 때는 `validateOracleWorkspace(검토파일, 원본사례)`로 연결을 확인합니다. `updateOracleEntry`가 반환한 작업 내용을 저장해야 변경이 남습니다.

검토자 이름은 본인이 기록하는 값입니다. 로그인이나 전자서명이 아니며, 해시도 검토자의 신원이나 정답의 진위를 인증하지 않습니다.

## 확인한 정답 내보내기

화면의 **확인한 정답 내보내기**는 확인 완료한 문항만 새 JSONL 파일로 다운로드합니다. 버튼에 표시된 완료 건수와 화면 상단의 전체 건수를 확인한 뒤 사용합니다. 수정 필요·보류·미검토 문항은 들어가지 않으며, 검토를 이어갈 때는 이 정답지가 아니라 앞에서 저장한 검토 JSON을 불러옵니다.

CLI에서도 저장한 검토를 원본과 대조한 뒤 내보낼 수 있습니다. `--cases`에는 검토를 시작할 때 사용한 원본 사례 파일을 지정합니다.

```bash
node dist/cli.js oracle-export --cases local/cases.draft.jsonl \
  --workspace local/oracle-review.json --out local/cases.verified.jsonl
```

기본 명령은 미완료 문항이 하나라도 있으면 내보내지 않습니다. 먼저 확인한 일부 문항으로 파일럿을 시작하려면 명시적으로 `--approved-only`를 붙입니다. 출력에는 포함한 문항 수와 제외한 문항 수가 표시됩니다.

```bash
node dist/cli.js oracle-export --cases local/cases.draft.jsonl \
  --workspace local/oracle-review.json --out local/cases.pilot.jsonl --approved-only
```

확인 완료한 문항이 없으면 내보낼 수 없습니다. 기존 출력 파일은 덮어쓰지 않습니다. 내보낸 사례에만 `review_status: verified`와 검토자가 반영되며, 가상 사례는 검토 후에도 `origin: synthetic`으로 남습니다. 정답을 확인했다고 실제 업무 사례나 독립 검증 사례로 바뀌지는 않습니다.

## 평가로 이어가기

```text
원문 대조·정답지 검토 → 확인한 정답 내보내기 → 새 prepare → 모델 실행 → 답변 채점
```

검토 상태나 검토자가 바뀌어도 사례 해시가 달라집니다. 내보낸 정답지로 새 실행 계획을 만들고 평가를 시작합니다. 이전 정답지로 만든 계획이나 모델 답변 검토 기록을 그대로 재사용하지 않습니다. 이후 명령은 [첫 실제 평가 준비](first-evaluation.md)를 따릅니다.

실제 CS와 비공개 자료가 담긴 원본 사례, HTML, 검토 파일과 내보낸 정답지는 `local/` 등 Git에서 제외한 위치에 보관합니다. 정답이 있다는 이유만으로 모든 사례의 공개를 막지는 않습니다. 공개 가능한 사례와 검토 결과는 내용과 출처의 공개 범위를 확인한 뒤 별도로 공유할 수 있습니다.

공개 여부와 관계없이 정답과 검토 내용은 평가자용 자료입니다. 모델 입력에 넣지 않으며, 평가 중 접근 범위도 분리해야 합니다. 팀 보관과 공개 보고서 작성 기준은 [평가 운영 흐름](evaluation-workflow.md#기록-보관과-공개)을 따릅니다.
