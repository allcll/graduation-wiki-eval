# 필수 Skill 본문 전달 준비 검증

2026-11-15, 기존 C 답변 20개 중 9개에서 PROJECT.md 읽기 요청이 없었던 문제를 보완했습니다. 이번에는 **모델을 호출하지 않고 입력 구성만 검증**했습니다. 이전의 읽기 누락을 성공으로 바꾸거나 새 답변 성능을 측정한 결과가 아닙니다.

## 바뀐 연결 방식

`--skill-delivery inline`에서는 어댑터가 요청의 필수 Skill 파일을 읽고, 경로와 전체 본문을 `skill_documents`에 넣습니다. 네이티브 Skill을 등록하거나 모델이 참조를 따라갈 때까지 기다리는 방식은 아닙니다. 이 모드의 지침에서는 관련 문서를 선택하라는 문구를 빼고 제공된 필수 문서를 모두 적용하도록 안내합니다.

본문 준비·참조 검사에 실패하거나 전달 기록을 저장할 수 없으면 모델 호출 전에 중단합니다. 기존 `--require-skill-reads` 모드는 그대로 유지하지만 inline과 동시에 사용하지 않습니다. 기존 파일 탐색 기반 C와 입력 조건이 달라 새 실험으로 기록해야 합니다.

## 저장된 실제 요청으로 확인한 것

| 항목 | 결과 |
| --- | ---: |
| C 요청의 필수 문서 포함 | 20/20 |
| 전체 본문과 파일 해시 일치 | 80/80 파일 |
| A/B 요청에 Skill 본문 미포함 | 40/40 |
| 질문·입력·기존 자료 목록·출력 계약 보존 | 60/60 |
| 추가 모델 호출 | 0회 |

실제 어댑터가 사용하는 `prepareClaudePayload` 함수에 저장된 요청을 넣었습니다. C 각각의 wrapper·query 본문·CLAUDE.md·PROJECT.md 전체 내용이 입력에 포함되고 원본 파일 해시와 일치하는지 확인했습니다. [요청별 입력 해시와 문서 목록](inline-skill-preflight.observations.json)을 남겼습니다. 본문 내용은 공개 기록에 넣지 않았습니다.

## 모의 프로세스로 확인한 것

- 실제 stdin 인자를 가로채 4개 본문과 질문·입력이 들어 있는지 확인했습니다. 모의 답변만 반환하므로 Claude 실행이나 인증 요청은 없습니다.
- 모델 실행 직전에 `skill-delivery.json`이 저장되어 있고, 그 해시가 전달할 stdin 문자열과 같은지 확인했습니다.
- 모델의 Read 이벤트가 없어도 inline 본문 전달과 Read 기록이 섞이지 않는지 확인했습니다.
- 빈 문서·잘못된 UTF-8·NUL·없는 참조·목록 밖 참조·순환·크기 초과·경로 이탈을 호출 전에 거부했습니다.
- 이미 있는 전달 기록을 덮어쓰거나 심볼릭 링크를 따라 기록하지 않았습니다.

이 검증이 보장하는 것은 필수 문서가 입력에서 빠지지 않는다는 점입니다. 모델이 지침을 이해하고 정확하게 적용하는지는 이후 별도의 실제 실행과 답변 검토가 필요합니다. 이번에는 구독 한도나 API를 사용하지 않았습니다.
