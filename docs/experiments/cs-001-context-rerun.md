# 질문 정의와 Skill 입력을 보완한 재평가

2026-11-15, 첫 실행과 같은 `CS-2026-2-001`을 A/B/C에서 한 번씩 다시 실행했습니다. **A와 B는 9학점, C는 6학점으로 답했습니다.** Skill 본문 누락은 보완했지만, C의 학점 해석 오류는 남았습니다.

## 무엇을 바꿨나

첫 실행에서는 인정 학점의 정의가 모호했고, C에 실제 Skill 본문 대신 연결 파일만 들어갔습니다. 이번에는 두 부분을 보완했습니다.

| 항목 | 변경 |
| --- | --- |
| `recognized_credits` | ‘이수 과목 중 인정 학점’ → ‘해당 요건에 포함되는 이수 과목들의 취득 학점 합계’ |
| `required_credits` | ‘필요한 학점’ → ‘해당 학생이 요건을 충족하기 위해 필요한 최소 학점’ |
| C의 Skill 자료 | wrapper의 상대 경로를 유지하고 본문·CLAUDE.md·PROJECT.md를 함께 제공 |
| 실행 전 검사 | `skill_contract`에 진입점과 필수 파일을 선언. `prepare`·`run`에서 누락·빈 본문·순환 참조를 차단 |

출력 설명에는 정답 숫자를 넣지 않았습니다. 질문 본문, 학생 조건, 정답값 9, 채점 기준, 편람 근거는 유지했습니다. 112건 릴리스를 고치지 않고 [문항 수정본](../../datasets/graduation-2026-2/pilots/cs-001-v2/README.md)으로 분리했습니다. 입력 정의가 바뀌었으므로 이전 승인 기록은 이어 붙이지 않고 `draft`로 남겼습니다.

원문 PDF·추출 텍스트와 WIKI의 INDEX·2022학번 균형교양 문서는 첫 실행과 해시가 같습니다. WIKI와 Skill 본문 자체는 수정하지 않았고, 모두 동일한 WIKI 커밋 `b7d05fcae2c8f588b2ed18e0fa4bc4f87d23512a`에서 읽었습니다.

## 실행 조건

- Claude Code 2.1.325, 요청 모델 `claude-sonnet-4-6`, effort `medium`
- 기존 Claude Pro 로그인. 사용자가 추가 사용량을 껐다고 확인한 상태에서 실행했으며 API 키나 API 방식으로의 우회는 사용하지 않음
- A/B/C 각각 1회, 최대 12턴·180초, 실행기 제한 210초
- 공통 지시, 모델, 허용 도구 Read/Grep/Glob은 첫 실행과 동일
- 정답·채점 기준·기존 응답은 모델 요청에서 제외

계정의 추가 과금 설정 자체를 코드가 조회한 것은 아닙니다. C에 들어간 자료는 Skill wrapper, 실제 query 본문, CLAUDE.md, PROJECT.md의 4개이며 A/B에는 제공하지 않았습니다. `skill_contract`는 자료 검사에 사용하고 모델 요청에는 넣지 않았습니다.

### C에 남은 오류

C는 세 과목을 모두 인정 대상으로 분류하면서도 다음과 같이 설명했습니다.

> 초과 이수한 3학점(동일 영역 중복분)은 균형교양 요건 계산에는 반영되지 않습니다.

이는 [원문 대조](cs-001-source-audit.md)에서 확인되지 않은 상한을 다시 적용한 것입니다. 같은 영역의 두 과목은 **영역 수로는 하나**지만, 그 이유만으로 서로 다른 이수 과목의 학점을 제외할 수는 없습니다. C의 최종 인용은 WIKI에 집중됐고 `2026-1 p.52`를 적었습니다. 질문에서 요청한 2026-2 원문과의 대조 근거는 최종 답변에서 확인되지 않았습니다.

이번 실행으로 본문 누락 여부와 답변 품질을 분리할 수 있게 됐습니다. 자료가 빠지지 않았다는 검사를 통과해도, 모델이 규정을 정확히 해석했다는 뜻은 아닙니다. 도구 호출 기록을 수집하지 않았으므로 실제로 Skill 본문이나 PDF를 읽었는지, 어느 문서가 오류에 영향을 줬는지는 단정하지 않습니다.

B도 숫자만으로 전체 통과시키지 않았습니다. 2026-2 기준이라고 설명하면서 인용은 WIKI 위주이고, 과거 `CategoryCreditCalculator` 버그를 이번 화면 표시와 연결하는 설명이 있습니다. 이 사례의 원인을 확인할 코드·현재 데이터는 제공하지 않았으므로 답변 범위와 근거를 사람이 검토해야 합니다.

## 해석 범위와 다음 평가

1건을 조건별 한 번만 실행했고 새 입력과 모델 답변의 사람 검토도 남아 있습니다. 독립 holdout은 없습니다. 따라서 품질 gate와 이전 버전 비교는 모두 `INCONCLUSIVE`입니다. `compare`가 입력 해시 변경과 미검토 상태를 감지하는 것을 확인했으며, B의 숫자가 맞아졌다는 관찰을 WIKI 개선률로 바꾸지 않았습니다.

이번 C는 **query Skill을 문서로 제공한 조건**입니다. 네이티브 Skill 자동 탐색·선택은 꺼져 있고, 문서가 요구하는 pdfplumber 실행도 Read/Grep/Glob 도구로는 수행할 수 없습니다. 본문 제공 검사를 실제 Skill 전체 수행의 증거로 사용하지 않습니다.

사용자가 언급한 백엔드의 `docs/agent-harness/skills/graduation-qa/SKILL.md`도 읽기 전용으로 확인했습니다. 이 Skill은 신고 배치 분류, WIKI 기반 기대 동작 확인, 데이터/코드 분기, 수정 전후 DB 리플레이·diff, PR까지 다룹니다. 정책 질의용 query보다 원래 목표인 QA 대응 자동화에 가깝지만, 현재 질문과 자료만으로는 전체 절차를 평가할 수 없습니다.

따라서 현재 정책 Q&A 결과는 보존하고, 다음 단계는 별도의 QA 평가로 구성합니다. 현재 신고와 수정 전 코드·기준 데이터, 검증 가능한 재현 환경을 준비하고 원인 분류·수정안·테스트 및 예상 밖 변경 여부를 채점합니다. 과거 해결 문서나 정답 패치를 입력에 섞지 않습니다. 어떤 Skill 파일을 읽고 도구를 실행했는지도 기록해야 절차 수행을 검증할 수 있습니다. 이번 재평가에 `graduation-qa`를 추가하거나 모델을 더 호출하지는 않았습니다.
