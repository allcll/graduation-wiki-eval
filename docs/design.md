# 평가 설계

졸업요건 WIKI에는 학번·전공별 규칙과 예외가 함께 있다. 문서가 정확해도 에이전트가 다른 학번의 규칙을 적용하거나, 예외를 놓치거나, 자료가 부족한 상태에서 원인을 단정할 수 있다. 이 도구는 그런 실패를 사례별로 확인하고 WIKI·Skill 변경 전후를 비교하기 위해 만든다.

평가 대상은 기존 ALLCLL WIKI와 Skill이다. 이 레포의 작업 범위는 평가 명세, 실행·채점 도구, 회귀 비교다. 기존 WIKI를 이 프로젝트에서 처음 구축했다고 주장하지 않으며, 다른 팀원의 벤치마크 결과를 이 평가의 성과로 사용하지 않는다.

## 비교 조건

| 조건 | 제공 자료 | 확인할 효과 |
| --- | --- | --- |
| A | 원본 편람·확인 자료, 과제에 필요한 코드·기준 데이터 | 원본 자료만으로 수행한 결과 |
| B | A + WIKI | 정리된 지식을 제공한 효과 |
| C | B + Skill | WIKI가 있는 상태에서 작업 절차를 추가한 효과 |

모델 버전·설정, 기본 지시, 도구, 권한, 출력 형식, 실행 제한은 같게 둔다. Skill에서 사용하는 검증 도구도 A/B에서 사용할 수 있어야 한다. Skill이 새로운 사실을 추가한다면 C−B에는 지식과 절차의 효과가 함께 들어가므로 이를 기록한다.

WIKI 제공 효과와 변경 효과는 별도 실험이다. 전자는 같은 버전에서 A/B/C를 비교한다. 후자는 같은 조건에서 WIKI 또는 Skill의 이전 버전과 개선 버전을 비교한다. 문서 구조만의 효과를 보려면 별도로 동일한 사실을 담은 평면 문서와 비교해야 한다.

## 정답셋

정답은 원문 편람이나 공식 확인 자료에서 작성한다. WIKI·기존 봇 응답을 복사해 정답으로 삼으면 WIKI의 오류를 평가셋에도 넣게 된다. 초안 작성에 AI를 사용하더라도 사람이 적용 대상과 원문을 확인한 뒤 검토 완료 상태로 바꾼다.

사례마다 다음을 남긴다.

- 질문과 입학년도·전공 등 입력 조건
- 같은 규정 또는 오류 원인을 묶는 `family`
- 원출처 버전·조항·페이지와 정답을 확정한 검토자
- 기대 행동(`answer`, `clarify`, `escalate`)과 구조화된 사실
- `rubric`에 판정 기준 버전과 반드시 설명해야 할 조건, 허용할 판단과 금지할 단정
- 개발용 `dev` 또는 최종 평가용 `holdout` 구분

편람·규정·확인 회신이 충돌하면 적용 시점과 범위, 정정 여부를 확인한다. 우선순위를 확정할 수 없다면 사람 확인 요청이 정답일 수 있다. 최신 자료라는 이유만으로 과거 입학생에게 적용하지 않는다.

원인 분류에는 코드·데이터·정책 해석뿐 아니라 복합 원인과 근거 부족도 포함한다. 정책과 데이터가 다르다는 관찰만으로 데이터 오류를 확정하지 않고, 해당 정책의 적용 가능성과 그 데이터가 실제 사용되는지 확인한다.

### 개발용과 최종 평가용의 분리

같은 규칙을 문장만 바꾼 사례나 같은 예외의 대응 사례는 하나의 `family`로 묶는다. 같은 family를 dev와 holdout에 나누지 않는다. 회귀 검사용으로 사용하는 기존 실패 사례는 dev에 두고 태그로 구분한다.

개선 중에는 dev의 결과만 확인한다. 개선 버전을 고정한 뒤 holdout에서 이전·개선 버전을 함께 실행한다. holdout의 질문이나 결과를 보고 개선했다면 그 사례는 이후 독립 검증에 사용할 수 없다. dev로 옮기고 새로운 사례군을 확보한다.

## 실행 기록과 자료 범위

실행 전에 사례·조건·반복 횟수를 정한다. 완료된 응답 수에 맞춰 계획을 줄이지 않는다. 각 실행에는 원문·코드·데이터·WIKI·Skill·모델·설정·채점기 버전을 남긴다. 사례와 출력의 해시로 검토 기록을 연결해, 답변이 바뀐 뒤 이전 검토를 재사용하지 않도록 한다.

외부 실행기는 작업별 요청 JSON을 입력으로 받고 응답 JSON을 반환한다. 요청에는 질문과 허용된 입력 자료를 제공하고, 평가자용 정답·검토 기록은 넣지 않는다. 실행마다 새 작업 디렉터리를 사용하며 자동 재시도로 실패를 덮어쓰지 않는다.

작업 디렉터리 분리는 OS 접근 제어가 아니다. 외부 실행 프로세스는 운영체제 권한에 따라 상위 폴더나 다른 자료를 읽을 수 있다. 실제 모델을 연결할 때는 평가자가 다음을 확인해야 한다.

- 새 대화 세션으로 실행하며 이전 응답·메모리·검색 캐시가 조건 사이에 유입되지 않는가
- 전역 Skill과 상위 디렉터리 지시가 A/B에 자동 로드되지 않는가
- 정답표·해결 PR·사후 분석·다른 실행 결과에 접근할 수 없는가
- 과거 오류 분석에는 수정 전 코드와 당시 유효한 자료를 제공했는가

이 조건을 확인할 수 없으면 격리된 실험이라고 쓰지 않는다. MCP 서버나 새 검색 시스템은 평가 도구의 필수 구성 요소가 아니다.

## 채점

자동 검사는 구조화된 `action`과 `facts`를 정답과 비교한다. 숫자·자료형·필드의 정확한 일치가 필요한 검사이므로, 실행 전에 모든 조건에서 같은 출력 계약을 사용한다. 표현이 다른 동의어를 자동으로 같은 뜻으로 처리하지 않는다.

자연어 답변은 사례에 미리 작성한 rubric의 항목별로 사람이 판정한다. 각 항목에는 고유 id, dimension, 설명을 적으며 두 dimension 모두 기준이 있어야 한다.

| 판정 | 검토할 내용 |
| --- | --- |
| `evidence` | 출처가 실제로 존재하고, 적용 가능하며, 핵심 주장을 뒷받침하는가 |
| `answer` | 답변 전체의 대상·조건·예외·원인 분류가 맞고, 모순이나 중요한 누락이 없는가 |

각 항목의 판정은 `pass`, `fail`, `pending`이며 완료 판정에는 이유를 남긴다. dimension별로 하나라도 fail이면 fail, fail 없이 pending이 있으면 pending, 모두 pass이면 pass로 집계한다. 한 항목이 실패했더라도 미검토 항목이 남아 있으면 검토 대기 상태를 유지한다. 모든 항목과 자동 검사를 통과해야 완전 성공으로 센다.

rubric 내용의 해시를 계획·검토·보고서에 결합한다. 기준을 바꾸면 새 사례 버전으로 평가하고, 기존 검토를 자동 승계하지 않는다. `review-template`이 만드는 사람용 Markdown에는 질문·정답·원답변·기준을 함께 보여주지만 모델 요청에는 이 자료를 넣지 않는다.

링크가 있다는 사실, Skill을 호출했다는 사실, 모델이 출력한 신뢰도 숫자는 사람 판정을 대체하지 않는다. 구조화된 숫자는 맞아도 본문이 그 숫자와 모순되면 실패다. 항목을 명시해도 사람 판정의 일관성이 자동으로 검증되는 것은 아니므로 첫 실측에서 실제 응답을 함께 검토하고 기준을 조정한다.

LLM 채점기는 기본 구성에 포함하지 않는다. 추후 도입한다면 사람이 채점한 자료로 판정 기준을 보정하고, 보정에 쓰지 않은 자료로 다시 확인한다. 특히 사람이 실패라고 한 답을 잘못 통과시키는 경우를 별도로 집계한다. 숫자·대상·근거를 의도적으로 바꾼 응답을 넣어 해당 오류를 탐지하는지도 검사한다.

## 결과 해석

계획한 실행 수를 분모로 유지한다. 미실행·실행 오류·검토 대기는 성공으로 세지 않고 별도 건수로 표시한다. 시간·토큰도 측정하지 않은 값을 0으로 채우지 않는다. 전체 결과와 함께 학번 경계·예외·정보 부족·원인 분류 등 유형별 실패를 확인한다.

품질 판정은 조건별 holdout 범위에 적용한다. dev 결과는 개발과 회귀 진단에 사용한다.

| 상태 | 의미 |
| --- | --- |
| PASS | 검토 완료된 실제 holdout의 계획 실행이 모두 완료되고 필수 검사를 통과함 |
| FAIL | 검토 완료된 실제 holdout에서 필수 조건 실패가 확인됨. 미확인 사항도 함께 기록 |
| INCONCLUSIVE | 합성 자료, 미검토 정답, 실행 누락·오류, 사람 검토 대기, 버전 혼합, holdout 부재 등으로 판단 근거가 부족함 |

이는 이 프로젝트의 초기 기준이며 기업 공통 기준이나 배포 승인이 아니다. 공개 예제는 가상 규칙을 사용하는 합성 자료다. 예제 실행이나 소프트웨어 테스트 통과는 실제 WIKI·Skill의 품질 측정 결과가 아니다.

변경 전후에는 같은 사례·조건·반복 번호를 맞춰 성공→실패, 실패→성공, 미변화를 기록한다. 평균이 같아도 새로 생긴 실패를 놓치지 않는다. 원문·코드·모델 설정 등이 함께 바뀌면 WIKI·Skill만의 변경 효과로 해석할 수 없다. 재실행에서 성공한 결과만 골라 최초 실패를 대체하지 않는다.

원문 정책 자체가 바뀌었다면 적용 시점과 정답셋을 먼저 갱신한다. 이때의 차이는 기존 정책을 더 잘 이해하게 된 효과와 구분한다. 같은 데이터셋이라고 표시한 채 정답을 바꾸지 않는다.

## 첫 실측

검토 완료된 대표 사례 3개를 A/B/C에서 한 번씩 실행해 입력·기록·채점과 비용을 확인한다. 9회 파일럿은 평가 절차 점검용이다. 그다음 사례군을 늘리고 분할을 고정해 실패 분석과 개선을 진행한다.

보고서에는 고유 사례 수와 반복 횟수를 따로 적는다. 적은 표본에서는 사례별 결과, 성공/전체 건수, 비용 범위를 우선 보고한다. 오프라인 점수 향상이 확인되더라도 실제 개발자 작업 시간이나 CS 해결 시간의 단축은 별도 운영 측정이 필요하다.

설계에 참고한 기업 사례와 적용 범위는 [참고 자료](references.md)에 정리했다.
