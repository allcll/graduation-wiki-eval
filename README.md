# graduation-wiki-eval

졸업요건 QA에 사용하는 WIKI와 Skill이 답변에 도움이 되는지 확인하는 TypeScript 평가 도구입니다. 같은 질문을 정해진 조건에서 실행하고, 답변과 근거를 검토한 뒤 문서 수정 전후의 결과를 비교합니다.

## 문제 상황

ALLCLL에서는 졸업요건 문의가 들어오면 개발자가 WIKI와 QA Skill을 활용해 원인을 분석합니다. 규정을 잘못 해석했는지, 기준 데이터가 다른지, 코드가 의도대로 동작하지 않는지 확인하는 과정입니다.

WIKI에 규정이 적혀 있어도 LLM이 이를 올바르게 적용한다고 보장할 수는 없습니다. 학점 숫자는 맞지만 다른 학번의 규정을 인용하거나, 일반 규칙만 보고 특정 학과의 예외를 놓칠 수 있습니다. 필요한 정보가 없는 문의에 추측해서 답하는 경우도 확인해야 합니다.

질문을 하나씩 넣어 답변을 확인하면 해당 사례의 문제는 찾을 수 있습니다. 하지만 WIKI를 수정했을 때 답변이 나아졌는지, 이전에 맞히던 질문에서 새 오류가 생겼는지 비교하려면 같은 질문과 판정 기준이 필요합니다.

## 해결 방안

문의 대응을 자동화하기에 앞서, 그 판단 근거가 되는 WIKI와 Skill을 반복해서 검증할 수 있도록 평가 절차를 만들었습니다.

1. 원문 편람과 공식 자료에서 질문별 정답·근거·채점 기준을 준비합니다.
2. 같은 질문을 원본 자료만 제공한 경우, WIKI를 추가한 경우, Skill 문서까지 추가한 경우로 나누어 실행합니다.
3. 정해진 사실값과 행동은 코드로 검사하고, 답변의 해석과 근거는 사람이 검토합니다.
4. 실패 원인을 찾아 WIKI·Skill을 수정하고, 같은 사례로 다시 평가해 개선과 회귀를 확인합니다.

기존 WIKI와 Skill은 평가 대상입니다. 이 레포에서 만드는 것은 평가 명세, 실행기, 채점·검토 도구, 보고서와 변경 전후 비교 기능입니다. 현재 평가 범위는 문서를 활용한 답변 품질이며, 네이티브 Skill 자동 선택·코드 수정·테스트 실행까지 포함한 전체 작업 성능은 아닙니다.

## 전체 흐름과 역할

```text
[사람] 질문·정답·근거·채점 기준 확정
   ↓
[코드] 사례 검사 → 조건별 자료 준비 → Claude Code 실행
   ↓
[LLM] 자료를 읽고 답변·판단 결과·인용 근거 작성
   ↓
[코드] 응답·오류 기록 → 자동 검사 → 사람 검토 양식 생성
   ↓
[사람] 답변의 대상·조건·예외·근거를 검토하고 이유 기록
   ↓
[코드] 보고서 생성 → 이전 결과와 비교
   ↓
[사람] WIKI·Skill 수정과 다음 작업 결정
```

평가 실행기는 자료와 호출 순서를 관리하고, Claude Code는 파일 검색·읽기 도구로 필요한 자료를 확인합니다. LLM은 답변을 작성하는 역할이며, 현재 채점은 코드와 사람이 나누어 담당합니다. 정답과 사람 검토 기록은 모델 요청에 넣지 않습니다.

사람이 하는 검토는 두 가지입니다.

| 구분 | 정답지 검토 | 모델 답변 검토 |
| --- | --- | --- |
| 확인할 것 | 준비한 정답과 근거가 맞는가? | 이번에 생성한 답변과 인용이 맞는가? |
| 시점 | 사례를 처음 만들거나 정답·근거·기준을 바꿀 때 | 새 모델 응답을 받은 뒤 |
| 현재 도구 | HTML 화면에서 검토·수정·저장·이어 하기 | Markdown으로 확인하고 JSONL에 항목별 판정 기록 |
| 재사용 | 정답과 기준이 그대로면 다음 평가에서도 사용 | 새 응답에 이전 판정을 임의로 재사용하지 않음 |

정답지 HTML은 모델 답변까지 채점하는 웹 대시보드는 아닙니다. 사용 방법은 [정답지 검토 화면](docs/oracle-review.md)에 정리했습니다.

## 무엇을 비교하는가

### WIKI·Skill을 제공한 효과

모델·기본 지시·도구·출력 형식·실행 제한을 같게 두고 제공 자료를 나눕니다.

| 조건 | 제공 자료 | 비교 목적 |
| --- | --- | --- |
| A | 원본 편람·공식 확인 자료와 필요한 코드·데이터 | 원본 자료만으로 수행한 기준선 |
| B | A + WIKI | 정리된 지식을 제공한 효과 |
| C | B + Skill 문서 | 확인 절차와 작업 지침을 추가한 효과 |

정답은 평가 대상인 WIKI나 과거 AI 답변을 복사해서 만들지 않고 원출처에서 확인합니다. Skill에 새로운 지식도 포함되어 있다면 C와 B의 차이를 절차만의 효과로 해석하지 않습니다.

### WIKI·Skill을 수정한 효과

같은 질문·정답·모델·실행 조건에서 기존 버전과 수정 버전을 각각 실행합니다.

| 결과 변화 | 해석 |
| --- | --- |
| 실패 → 성공 | 개선된 사례 |
| 성공 → 실패 | 새로 생긴 회귀 |
| 실패 → 실패 | 아직 해결하지 못한 사례 |
| 성공 → 성공 | 기존 품질을 유지한 사례 |

모델이나 정답셋까지 바뀌었다면 WIKI 수정만의 효과로 비교하지 않습니다. 최초 실패는 보존하고, 재실행에서 성공한 결과로 덮어쓰지 않습니다.

## 어떤 답변을 좋은 답변으로 보는가

해당 학생에게 적용되는 규정을 올바르게 해석하고, 확인 가능한 근거를 제시하며, 정보가 부족할 때 필요한 확인을 요청하는 답변을 목표로 합니다.

| 기준 | 확인할 내용 | 판정 방법 |
| --- | --- | --- |
| 사실·행동 | 정해진 사실값과 기대 행동이 맞는가? | 구조화된 `facts`·`action`을 정답과 자동 비교 |
| 적용 대상 | 입학 연도·학과·예외 조건을 올바르게 적용했는가? | 사람 검토 |
| 근거 | 실제 출처가 존재하고 해당 주장을 뒷받침하는가? | 사람 검토 |
| 불확실성 처리 | 정보 부족이면 질문하고 규정 충돌이면 확인을 요청하는가? | 행동 자동 비교 + 답변 검토 |
| 일관성 | 결론과 설명이 모순되지 않고 중요한 조건이 빠지지 않았는가? | 사람 검토 |

문항별 채점 기준인 rubric을 응답 생성 전에 작성합니다. 검토자는 각 항목에 `pass`·`fail`·`pending`과 이유를 남깁니다. 모델이 출력한 자신감이나 링크의 존재만으로 통과시키지 않습니다. 자동 값 비교도 자연어 답변 전체의 정확성을 보장하지는 않습니다.

### 오류 심각도와 품질 판정

| 심각도 | 의미 | 판정 |
| --- | --- | --- |
| `blocker` | 잘못된 졸업 충족 판단처럼 결과를 신뢰할 수 없게 만드는 문제 | 필수 실패 |
| `major` | 적용 규정이나 중요한 예외 설명이 빠지는 문제 | 필수 실패 |
| `minor` | 결론을 바꾸지 않는 반복·표현 등의 개선점 | 개선 권고 |

자동 사실값·행동 검사 실패도 필수 실패입니다. minor만 실패한 실행은 다른 조건을 충족하면 통과할 수 있지만, minor라도 검토하지 않았다면 미완료입니다. 심각도는 문항을 준비할 때 정하며, 결과를 통과시키려고 사후에 낮추지 않습니다.

개선하며 보는 `dev`와 마지막에 확인하는 독립 사례 `holdout`을 규정·원인군 단위로 나눕니다. 같은 규칙을 문장만 바꾼 사례가 양쪽에 걸치지 않게 합니다. holdout을 보고 수정했다면 해당 사례는 이후 독립 검증에 다시 사용하지 않습니다.

최종 품질 판정은 조건별 holdout에 적용합니다.

| 상태 | 의미 |
| --- | --- |
| `PASS` | 검토된 실제 holdout의 계획 실행과 검토가 끝나고 필수 기준을 통과함 |
| `FAIL` | 검토된 실제 holdout에서 필수 조건 실패가 확인됨 |
| `INCONCLUSIVE` | 독립 사례 부재·미검토·실행 오류·누락 등으로 판단 근거가 부족함 |

현재는 합성 자료가 섞인 실행을 실제 성능 PASS로 처리하지 않습니다. 최초 dev 파일럿에서 전부 맞혀도 holdout 판정은 `INCONCLUSIVE`일 수 있습니다. 사례별 결과는 보고서에서 확인할 수 있으며, 오류·누락·검토 대기를 분모에서 빼지 않습니다.

프로그램 테스트 통과, 평가 실행 완료, WIKI 품질 PASS는 서로 다른 결과입니다. PASS도 해당 사례 범위의 결과이며 전체 서비스의 정확성이나 자동 배포를 보장하지 않습니다. 자세한 판정 규칙은 [평가 설계](docs/design.md)에 있습니다.

## 상황별 실행 흐름

### 처음 WIKI를 평가할 때

1. 원문에서 정답을 확인한 실제 사례를 고릅니다. 2026-2 편람을 기준으로 준비하되, 입학 연도별 적용 범위도 함께 확인합니다.
2. 정답지 검토 화면에서 질문·정답·근거·채점 기준을 확인하고 평가용 파일로 내보냅니다.
3. 로컬에서 A/B/C를 실행하고 실제 모델 응답을 저장합니다.
4. 사람이 답변과 근거를 검토한 뒤 보고서를 생성합니다.
5. 실패 유형과 개선할 부분을 기록합니다.

첫 파일럿은 검토 완료된 실제 사례 3개 × A/B/C = 9개 작업으로 시작합니다. 연결과 검토 절차를 확인하는 단계이며 전체 성능을 입증하는 표본은 아닙니다. 이후 사례군과 반복 횟수를 늘려 평가합니다.

### WIKI·Skill을 수정할 때

기존 버전과 수정 버전을 같은 사례로 실행하고, 각 응답을 검토한 뒤 `compare`로 개선과 회귀를 확인합니다. 현재는 로컬에서 실행하며, WIKI 변경 PR에서 자동 실행하는 연결은 후속 작업입니다.

### 새로운 CS가 들어왔을 때

기존 QA 절차로 원인을 분석하고 대응합니다. 평가 체계가 완성될 때까지 해결을 미룰 필요는 없습니다. 이후 개인정보를 제거하고 공식 근거로 기대 결과를 확인해 개발·회귀 검사용 사례에 추가합니다. 이미 해결한 CS도 재발 확인에 활용할 수 있지만, 그 사례를 보며 개선한 결과를 독립 holdout 성과로 보고하지 않습니다.

### 편람·정답·채점 기준이 바뀌었을 때

적용 대상과 시점을 확인한 뒤 정답지부터 다시 검토합니다. 새 평가셋·실행 계획으로 평가하고 기존 판정을 그대로 재사용하지 않습니다. 정답 자체가 바뀐 것과 같은 정답에 더 잘 답하게 된 것을 구분합니다.

### CI에서 실행할 때

수동 평가는 사람이 명령이나 GitHub 실행 버튼으로 시작하고, PR 평가는 변경 이벤트로 시작합니다. 로컬·CI는 실행 장소의 차이이며, 실제 답변을 평가하려면 두 곳 모두 모델 호출이 필요합니다.

| 실행 경로 | 현재 동작 또는 계획 |
| --- | --- |
| 이 평가 도구 레포의 PR | 고정 응답 예제로 실행·보고서 기능을 확인하고 같은 PR 댓글을 갱신 |
| 실제 모델의 수동 CI | 비공개 레포용 재사용 workflow 구현. 실제 WIKI 자료·키 연결과 검증은 진행 전 |
| 실제 WIKI 변경 PR | 같은 사례로 변경 전후 평가 후 댓글 갱신 예정. 트리거·자료 연결 필요 |
| 수동 평가의 디스코드 알림 | 보고서 요약과 검토할 작업을 팀 채널로 전송할 예정. 아직 미구현 |

먼저 로컬 실제 평가를 확인하고 결과 전달을 보완한 뒤 수동 CI와 WIKI PR 평가를 연결합니다. 현재 명령은 [GitHub Actions 연결](docs/actions.md), 후속 계획은 [평가 운영 흐름](docs/evaluation-workflow.md)을 참고하세요.

## 팀 공유 데이터셋

공개 가능한 112개 문항·정답·채점 기준·검토 기록을 [datasets/](datasets/README.md)에서 실행 도구와 함께 버전 관리합니다. WIKI는 평가 대상 지식으로 분리하고, 평가셋은 모델 입력에 포함하지 않습니다. `dataset-check`로 파일과 승인 기록을 확인하고, 공식 배포처에서 편람을 받은 뒤 `dataset-review`로 다른 컴퓨터에서도 열리는 검토 폴더를 만듭니다. [팀 사용 절차](docs/team-dataset.md)를 참고하세요.

## 실행하기

Node.js 22 이상이 필요합니다. 외부 어댑터 실행은 macOS/Linux를 지원합니다.

### 모델 없이 도구 동작 확인

```bash
git clone https://github.com/allcll/graduation-wiki-eval.git
cd graduation-wiki-eval
npm ci
npm run build
node dist/cli.js demo --out artifacts/demo
```

가상 규정 3개를 A/B/C에서 실행하고 `artifacts/demo/report.json`과 `report.md`를 만듭니다. 고정 응답을 사용하므로 모델 호출과 API 비용은 없습니다. 품질 판정은 `INCONCLUSIVE`이며 실제 WIKI의 성능 점수가 아닙니다. 재실행에는 새 출력 경로를 사용합니다.

### 실제 자료로 평가

[첫 실제 평가 준비](docs/first-evaluation.md)에 준비물과 실행 명령을 순서대로 정리했습니다. 정답지 검토부터 시작한다면 다음 명령으로 HTML을 만들 수 있습니다.

```bash
node dist/cli.js oracle-review --cases local/cases.draft.jsonl --out local/oracle-review.html
```

`local/cases.draft.jsonl`은 준비한 사례 파일입니다. 브라우저에서 원문과 대조한 뒤 검토 파일을 저장하고, 확인한 정답을 평가용 파일로 내보냅니다. 이후 `validate → prepare → run → review-template → 사람 검토 → report → compare` 순서로 진행합니다. 변경 전후를 비교할 때는 두 버전을 각각 실행해야 합니다.

실제 호출은 `평가 실행기 → TypeScript 어댑터 → Claude Code CLI → Anthropic 모델 API`로 이어집니다. 현재는 로컬에서도 `ANTHROPIC_API_KEY`가 필요하며, 구독 로그인 모드와 API 직접 호출 어댑터는 없습니다. MCP 서버는 필요하지 않습니다. 설치·인증·실행 제한은 [모델 연결](docs/adapters.md)에 설명했습니다.

패키지를 설치하면 `grad-eval`과 `grad-eval-claude` 명령을 사용할 수 있습니다. `report --check`는 모든 조건의 holdout 판정을 검사하며, C만 통과 기준으로 정했다면 `--check --condition C`를 사용합니다. A/B 결과는 보고서에 유지합니다. [입력 형식·종료 코드·버전 변경](docs/data-format.md)에 세부 사용법이 있습니다. v0.3 이하의 기록은 현재 v0.4 형식으로 변환해야 합니다.

## 기록과 결과 공유

응답·오류·실행 조건은 실행별 출력 폴더에 남고, 사람 검토를 반영하면 JSON·Markdown 보고서를 생성합니다. `local/`과 `artifacts/`는 Git에서 제외되어 GitHub로 자동 전송되지 않습니다. 원본 기록을 없애거나 모든 결과의 공개를 금지하는 뜻은 아닙니다.

| 자료 | 보관·공유 방식 |
| --- | --- |
| 학생 정보·실제 CS 원문·비공개 WIKI | 로컬 또는 접근을 제한한 팀 저장소 |
| 공개 가능한 질문·정답·채점 기준 | 내용과 출처를 확인한 뒤 레포에서 버전 관리 |
| 답변·검토 의견·보고서 | 원본 실행을 유지하고 공개 가능한 내용을 별도로 공유 |
| 전체 로그·중간 파일 | 실행별 폴더 또는 CI artifact |

공개 보고서는 사용한 버전·평가 범위·실패 이유·수정 PR·재평가 결과와 한계를 함께 남깁니다. 정답은 공개 여부와 관계없이 모델 입력과 실행 중 접근 범위에서 분리해야 합니다. 현재 실행기가 OS 샌드박스를 만들지는 않으므로 실측 환경의 접근 범위는 별도로 확인해야 합니다.

향후 같은 보고서를 PR 댓글과 수동 평가의 디스코드 알림에 사용합니다. 실행 상태와 품질 판정, 검토 대기, 실패 이유·개선 방향·상세 보고서 링크를 표시할 계획입니다. 사람 검토 전에는 검토 대기로 남기고, 검토 후 재채점한 결과를 전달합니다. 저장된 답변의 재채점이나 알림 재전송에는 모델 재호출이 필요하지 않습니다.

## 개발과 참고 자료

```bash
npm run check          # 타입 검사, 빌드, 테스트
npm run check:package  # 설치한 패키지의 CLI·라이브러리·검토 HTML·데모 확인
npm pack               # CLI·라이브러리·예제·문서를 포함한 패키지 생성
```

입력 JSON은 Zod로 검증하고 TypeScript 타입과 함께 관리합니다. `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`를 사용합니다. CLI 입출력과 채점 로직을 분리해 평가 함수·타입을 라이브러리에서도 사용할 수 있게 했습니다.

자료·설정·정답·응답·채점 기준의 해시를 기록해 변경된 응답에 이전 검토가 붙지 않도록 합니다. 타임아웃과 누락도 실행 기록으로 보존하며, 시작한 실험은 덮어쓰지 않습니다.

`src/schema.ts`는 입력 계약, `runner.ts`는 자료 준비·실행 기록, `evaluate.ts`와 `compare.ts`는 채점·회귀 비교, `cli.ts`는 명령행 연결을 담당합니다. 변경은 작업 브랜치와 PR로 진행하며 [PR 양식](.github/pull_request_template.md)에 문제·작업·검증 근거를 남깁니다.
